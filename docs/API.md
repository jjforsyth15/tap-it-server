# API Documentation

## Overview

The TapIt backend exposes a RESTful API used by the React frontend to manage authentication, user profiles, NFC cards, profile links, and beta feedback.

All requests and responses use JSON unless otherwise noted (such as multipart form uploads for avatar images).

Interactive API documentation is automatically generated by FastAPI and is available when the backend is running:

* `/docs` — Swagger UI
* `/redoc` — ReDoc documentation

---

```

Production

```

# Authentication

TapIt uses JSON Web Tokens (JWT) for authentication.

After a successful login, the backend returns an access token which must be included in all protected requests.

Example:

```http
Authorization: Bearer <access_token>
```

Protected endpoints automatically validate the token before processing the request.

If authentication fails, the API returns:

```http
401 Unauthorized
```

If a user attempts to access or modify resources they do not own, the API returns:

```http
403 Forbidden
```

Passwords are securely hashed before storage and are never stored in plain text.

# API Structure

Endpoints are grouped by resource.

## Authentication

Responsible for user registration and login.

Typical operations include:

* Register user
* Login
* Token validation

---

## Users

Provides authenticated user information.

Typical operations include:

* Retrieve current user

---

## Profiles

Responsible for profile management.

Typical operations include:

* Create profile
* Retrieve profile
* Update profile
* Retrieve user's profiles

Public profile endpoints are available without authentication.

---

## Profile Links

Manages links displayed on public profiles.

Typical operations include:

* Retrieve links
* Add link
* Delete link
* Reorder links

Only the profile owner may modify links.

---

## Cards

Responsible for NFC card management.

Typical operations include:

* Activate card
* Update card
* Retrieve assigned cards
* Retrieve public card information

Public card endpoints allow NFC taps to resolve to the appropriate public profile.

---

## Feedback

Stores beta feedback submitted by users.

Typical operations include:

* Submit feedback

Feedback includes optional metadata such as browser information, page URL, application version, and screen size.

---

# Public vs Protected Endpoints

## Public

Public endpoints do not require authentication.

Examples include:

* Public card lookup
* Public profile retrieval

These endpoints are intended to be accessed by anyone with a valid profile or card identifier.

---

## Protected

Protected endpoints require a valid JWT.

Examples include:

* Profile creation
* Profile editing
* Link management
* Card management
* User information
* Feedback submission (when associated with an authenticated user)

Ownership checks are performed to ensure users may only modify their own resources.

---

# Request Format

Most endpoints accept JSON request bodies.

Example:

```json
{
  "profile_name": "John Doe",
  "bio": "Software Engineer"
}
```

Avatar uploads use multipart form data.

---

# Response Format

Successful responses return JSON.

Example:

```json
{
  "profile_id": "...",
  "profile_name": "John Doe",
  "bio": "Software Engineer"
}
```

---

# Error Responses

Application errors follow a consistent structure.

Example:

```json
{
  "detail": "Profile not found"
}
```

FastAPI validation errors return additional validation details when request data is invalid.

---

# Common HTTP Status Codes

| Code | Description                                            |
| ---- | ------------------------------------------------------ |
| 200  | Request completed successfully                         |
| 201  | Resource created successfully                          |
| 400  | Invalid request                                        |
| 401  | Authentication required or token invalid               |
| 403  | User is not authorized to perform the requested action |
| 404  | Requested resource was not found                       |
| 422  | Validation failed                                      |
| 429  | Too many requests (rate limited)                       |
| 500  | Internal server error                                  |

---

# Rate Limiting

To improve application security and reliability, selected endpoints are protected using request rate limiting.

Examples include:

* Authentication
* Card activation
* Profile creation
* Link creation
* Feedback submission

Clients exceeding the configured request limit receive:

```http
429 Too Many Requests
```

The API includes several security measures:

* JWT authentication
* Password hashing
* Authorization checks
* Server-side validation
* Global exception handling
* Request logging
* CORS configuration
* Rate limiting
* Database transaction rollback on failures
